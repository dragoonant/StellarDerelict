# 40 — The Molt AI (M4)

`src/ai/molt/` plays the Molt seat. It is pure and deterministic: `(state, tier, seed)` gives one `Action`. It reads
`view(state, 'molt')` only (never the RNG, never the bag order; its one use of `step` is on a clone with a throwaway
dice stream and no bag), keeps no memory between calls (every call re-plans the phase from the board, so a reopened save
plays the same), and reads no clock unless one is injected (`opts.clock`, `opts.budgetMs`: only the optional lookahead stops early).

## Entry point and tiers (`src/ai/tiers.ts`)

`chooseMoltAction(state | view, tier, seed | rng, opts?) -> Action`, `tier` in `recruit | regular | veteran`.

| Tier | Plays as | Deliberate limits |
|---|---|---|
| `regular` | `moltPolicy` from `src/ai/scripted.ts`, unchanged | the scripted bot of the balance record |
| `veteran` | the utility AI below | none |
| `recruit` | the utility AI | no group reveal (a ping reveals alone once a Warden is within 5 steps), every strike square valued alike (ignores flanks), no ganging bonus, ignores watch fire and the Warden phase's guns (`cover` 0), idles each unit for a whole phase with probability 0.35 (hash of state seed, round and unit id), and any unit more than 8 squares from every Warden holds still |

The client picks the tier from `?bot=recruit|regular|veteran` (`?bot=random` keeps the random bot), else from the mission's
saved `setup.options.difficulty`, set by the Briefing's **Difficulty** choice (default Regular). Continue and the Debrief name it.

## Decision kinds

A call classifies the board into decision kinds; each has one policy in `POLICIES: Record<DecisionKind, Policy>`.
`ACTION_CLASS: Record<Action['type'], ...>` and `PENDING_KIND: Record<Pending['kind'], DecisionKind>` are exhaustive maps,
so a new action type or pending kind does not compile until it has a kind (`src/ai/molt/kinds.ts`).

| Kind | Actions | What the policy does |
|---|---|---|
| `arrive` (pending) | `arrive` | scores each open duct (below), takes the best |
| `pingMove` | `move`, `door` by a ping | walks to the best hold square among those it may legally reach, never into a seen square |
| `pingReveal` | `reveal` | reveals when the strike it would make is worth enough (group rule below) |
| `stalkerAct` | `move`, `door`, `tear`, `melee` by a stalker | melee when it pays; else one-ply over every square it can reach, first step to the best |
| `endPhase` | `endPhase` | score 0.05: taken when nothing scores higher |

Candidates of every open kind share one scale and the best legal one is played (ties: seeded jitter). A candidate the
engine refuses is skipped (`aiStats.rejected`); if none is left, or the policy throws, a random legal action is played and
counted (`aiStats.fallbacks`, printed by the bench). The top candidates that are a `door` or `move` are also run through
`step` on a clone; each forced reveal of one of our own pings in sight costs 6.

## Phase plan (recomputed per call, cached by a board signature)

- **Threat map.** Each watching Warden with shots left (`heat < lock`, or any held CP) kills a stalker that finishes a move,
  door or tear on a square it sees within 12 with the `query.hitChance` odds (lit squares included). `watchKill(sq) = 1 - prod(1 - p)`.
- **Exposure map.** What the Warden phase will do to a stalker left on a square: repeaters with line of sight (2 shots in
  the arc, 1.5 outside it), the scorcher within 6 with charges (0.65). Adjacent counts as in sight.
- **Route.** The squad's shortest way to its objective (the console's neighbours until the core is taken, then the airlock,
  or the dropped core) with the heading on each square; `routeSeen(sq)` counts route squares whose arc would see `sq`.
- **Targets.** Value of destroying a Warden `K = 10`, `+14` carrier, `+3` Tech while a bulkhead is still sealed, `+3`
  Sergeant, `+2` Scorcher, `+1` locked repeater, `+1.5` isolated (no Warden within 3), `+0.5` not on watch. A breach is
  worth `0.45 K` (`0.6 K` when two or more Molt units can reach that Warden this phase: ganging, A-1).
- **Attack runs.** `combat.ts` tabulates one stalker's value over `k` attacks: the first from the real facing (flank: the
  Warden cannot win, M-4), later ones frontal because a surviving Warden turns to face the attacker. Same arithmetic as
  `query.meleeOdds` (a unit test compares them).

## Scoring (veteran)

| Term | Value |
|---|---|
| Stalker `V(s)` on square `s` with `a` AP left | `attack run from s` `- 0.5 x G(s)` `- 6 x exposure(s)` `- 6 x (1 - path survival)` `- 1.5` per adjacent friend in the scorcher's sight `+ 0.8` standing in the carrier's route after the core is out |
| `G` | goal field: cost to the nearest strike square of any Warden (1 per step, door +1, sealed door +3.5, 0.3 x 4 x watch kill), starting at `-1.2 x` the value of a 5-attack run from that square, so flank squares pull harder |
| Melee candidate | `win x (K or breach + rest) + tie x rest - lose x 3`, from `query.meleeOdds` |
| Move candidate | `V(best reachable) - V(doing nothing)`; door, sealed door (expected 4 AP) priced in the path |
| Tear candidate | `0.4 x` goal-field gain through the sealed door `- 6 x` watch kill |
| Ping hold square | `4 - 0.9 x |steps from the route - 3|` (far squares keep a gradient), `- 2.5 x min(3, routeSeen)`, `- 2` if any Warden has line of sight |
| Ping reveal (group) | the best strike its stalkers can make this phase (second and later stalkers `x 0.85`, one AP less): reveal at `>= 2.5`, or `>= 1` in the last two rounds or when the carrier is within 10 steps of the airlock |
| Arrival duct | `-` route distance, `-0.25 x` distance to the nearest other Molt unit, `-1.5` if a Warden has sight of it |

## Cost budget and worker

Average decision <= 30 ms, worst <= 250 ms on the cloud container, a whole game <= 1.5 s (measured by the bench: see spec
10 §13b). `src/ai/worker.ts` runs `chooseMoltAction` off the main thread; `src/ai/workerClient.ts` wraps it and, if the
worker cannot start, errors or stops answering, logs one console warning and runs the same function on the main thread.

## Bench gates (`npm run bench:ai -- --games 400`, scripted Wardens, seeds 1..N, invariants on)

| Gate | Condition |
|---|---|
| veteran vs regular | veteran Molt win % >= regular + 10 points |
| recruit vs regular | recruit Molt win % <= regular - 10 points |
| recruit vs random | recruit Molt win % >= random Molt win % + 15 points |
| veteran fallbacks | 0 |
| safety | 0 invariant violations, 0 stalls |
| veteran speed | average decision <= 30 ms |

The two recruit gates can both hold only if the random Molt wins at least 25 points less often than the regular one.
Against the scripted Wardens it wins about 24 points more often (it fills the corridors with idle units and the scripted
Wardens run out of clock), so the recruit-vs-random gate fails by construction; the bench reports it and prints that note.
